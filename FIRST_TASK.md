# FIRST_TASK.md — первый этап разработки в Codex

**Комплект:** 1.1 · **Дата:** 18.11.2026.  
**Результат:** воспроизводимый каркас Rust + WASM + React/TypeScript + PixiJS с интерактивной тестовой картой. Это технический старт, ещё не игровая партия.

Прочитай `AGENTS.md`, `SPEC.md` и фактическое состояние репозитория. Выполни весь описанный здесь этап, включая запуск, проверки и исправление проблем в его пределах. Если часть уже реализована, проверь её и дополни недостающее; не заменяй существующий проект новым шаблоном.

## 1. Соответствие дорожной карте

- **T-001:** каркас, инструментальная цепочка, локальные проверки и инструкции запуска.
- **Часть T-002:** дискретная геометрия `Hex` и её тесты. `Map`, полная `HexEdge`, загрузчик и валидация сценария здесь ещё не требуются.
- Ранняя проба Rust→WASM→TypeScript и тестовый renderer проверяют интеграцию, но **не закрывают T-009/T-010** с полноценным игровым API и рендером сценария.
- Настроенный CI провайдера не является условием этого первого этапа. Локальные проверочные скрипты обязательны. Сохрани и используй существующий CI, если он есть; окончательная hosted-конфигурация относится к T-019.

## 2. Что реализовать

### 2.1. Структура и инструменты

Создай или дополни Rust workspace с `crates/game-core`, `crates/game-wasm`, минимальным `crates/game-ai`, веб-приложением `apps/web` и каталогом `content/scenarios`. Минимальный AI crate не должен содержать фиктивного противника. Пустой каталог контента можно отметить README, не выдавая его за готовый сценарий.

Настрой React, TypeScript `strict`, Vite, PixiJS 8 и pnpm. Выбери совместимые доступные стабильные версии инструментов при реализации; зафиксируй конкретные версии Rust toolchain, Node/pnpm и зависимостей в соответствующих файлах и lockfiles. Не подставляй непроверенные «последние» версии. Добавь `.gitignore`, сохрани корневой `SPEC.md` и существующие документы.

### 2.2. Дискретная геометрия

В `game-core` реализуй `Hex { q: i32, r: i32 }`, стабильный порядок шести соседей и расстояние по axial-сетке из SPEC. Рассчитывай разности в достаточной разрядности либо явно проверяй допустимый диапазон, чтобы не допустить переполнения.

Пиксельные преобразования `hexToPixel`/`pixelToHex`, cube rounding, камера и zoom находятся **в TypeScript renderer**. Floating point допустим там; его нет в игровых правилах `game-core`. Выбранная клетка передаётся в Rust как целочисленные координаты.

### 2.3. Настоящая WASM-интеграция

Используй `wasm-pack build crates/game-wasm --target web --out-dir pkg`. Генерируемый пакет находится в `crates/game-wasm/pkg`, включён в `.gitignore` и создаётся сборкой, а не ручным копированием файлов.

Экспортируй минимальную функцию вроде `hex_distance`, вызывающую реализацию в `game-core`. Используй сгенерированные JS/TypeScript-объявления. Выполни настоящий асинхронный `await init()` пакета перед использованием WASM; покажи состояние загрузки и понятную ошибку при неудаче. Не добавляй тихий расчёт-замену на JavaScript.

Настрой Vite так, чтобы ES-модуль и `.wasm` корректно работали в dev и production build. Не рассчитывай на глобальные переменные или незафиксированные файлы с машины разработчика. Не отключай ограничения доступа dev-сервера ко всей файловой системе ради импорта пакета.

### 2.4. Тестовая карта и интерфейс

- Pointy-top карта не меньше 10×8 клеток с axial-границами `0 <= q < width`, `0 <= r < height`, как в SPEC. Такая область выглядит параллелограммом; прямоугольная форма на экране сейчас не требуется.
- Простые собственные цвета местности, видимая граница/выделение клетки. Тестовые цвета не означают реализованные игровые свойства местности.
- Клик выбирает клетку; React-панель показывает `(q, r)` и расстояние до `(0, 0)`, полученное **через WASM**.
- Drag панорамирует камеру; колёсико масштабирует карту; размер canvas корректно меняется вместе с окном. После pan/zoom picking остаётся корректным. Drag не должен случайно исполнять клик выбора.
- Корректно обработай асинхронную инициализацию PixiJS и повторное монтирование React: без дубликатов canvas, обработчиков и утечек после unmount.
- Полноценные touch-жесты, боевой HUD и адаптация WebView относятся к следующим этапам.

## 3. Контракты скриптов

В корневом `package.json` создай следующие команды. Внутренняя реализация может использовать вспомогательные скрипты, но не должна содержать циклических вызовов или необъяснимых ручных шагов.

| Команда | Обязательный результат |
|---|---|
| `pnpm wasm:build` | Сборка реального пакета `crates/game-wasm/pkg` с target `web` |
| `pnpm dev` | Автоматическая подготовка WASM и запуск Vite; работает после чистого checkout и установки зависимостей |
| `pnpm build` | Подготовка WASM, проверка типов и production build веб-клиента |
| `pnpm typecheck` | Подготовка нужных generated typings и TypeScript-проверка без emit |
| `pnpm lint` | Проверка стиля/ошибок TypeScript настроенным линтером |
| `pnpm test` | Нативные Rust-тесты и содержательные TypeScript unit-тесты геометрии renderer |
| `pnpm test:e2e` | Реальный browser smoke test, включая вызов Rust/WASM и взаимодействие с картой |
| `pnpm check` | Совокупная проверка Rust fmt/clippy/tests, TS lint/typecheck/tests, production build и browser smoke |

Не повторяй одинаковые тяжёлые проверки внутри `check` без необходимости: собери цепочку зависимостей один раз. `test:e2e` должен самостоятельно подготовить нужный build/server или использовать корректно объявленный webServer в конфигурации теста.

Обязательные Rust-команды:

```bash
cargo fmt --all --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

README после реализации должен содержать реальные prerequisites и команды: установка выбранных версий, target `wasm32-unknown-unknown`, установка `wasm-pack`, установка JS-зависимостей, браузера тестов, запуск и проверка. Документируй первый `pnpm install` и повторяемую установку по lockfile. Секреты, аккаунты Telegram/VK и сервер не требуются.

## 4. Содержательные проверки

**Rust:** шесть уникальных соседей на расстоянии 1; симметрия расстояния; расстояние клетки до себя 0; отрицательные координаты; несколько контрольных пар, например `(0,0)→(2,-1) = 2`; обработка выбранных границ допустимого диапазона.

**TypeScript:** roundtrip центров `hex→pixel→hex`, в том числе с отрицательными координатами; picking после camera transform. Не дублируй в тестируемом production TS модуле игровую формулу расстояния.

**Браузер:** небольшой автоматизированный smoke test, например на Playwright/Chromium. Проверить загрузку страницы и `.wasm`, успешную инициализацию, выбор заранее известной клетки, отображение ожидаемого Rust-результата, корректность выбора после pan/zoom, отсутствие ошибок приложения и неудачных запросов обязательных ассетов. Не засчитывать JS mock вместо WASM. Для проверки воспроизводимости проверить production build, а не только dev server.

Если установка зависимостей, браузер или другой обязательный шаг блокируется окружением, зафиксируй точную причину, выполни остальные доступные проверки и явно пометь критерий `not run`. Не объявляй этап полностью принятым до выполнения обязательных проверок.

## 5. Что не входит

Боёвка, снабжение, система ходов, действующий AI, игровые сохранения, загрузка полного сценария, редактор, авторизация, Telegram/VK SDK, сервер, мультиплеер, платежи, Tauri и исторические ассеты. Не добавляй их «на будущее» вместе с каркасом. Не создавай вторую симуляцию в JavaScript.
